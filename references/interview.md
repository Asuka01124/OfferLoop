# 面试与评分流程

本文件规定如何提问和判断回答；可提交的JSON及状态转换见[评分v2的数据与交互](scoring-v2.md)，命令见[数据约定与命令](data-and-cli.md)。

## 选题与准备

先读取已有题库，确定使用者的岗位、方向、题量和模式。默认逐题练习、5道主问题；本次已经明确的信息直接采用。按近期有效来源选题，不用过期题或生成题静默补足数量。继续面试时恢复原会话，不重新选题。

在提问前核对技术资料，准备v2评分表，再保存会话快照。评分表说明考察目标、必要前提、可以接受的替代解释、不要求覆盖的扩展知识，以及每个维度需要观察的证据。参考答案用于帮助判断，不是关键词检查表；不能在看过回答后为了迎合或否定它更改本场标准。

| 题型 | 主要观察 |
| --- | --- |
| 基础问答 | 是否理解机制，能否解释成立条件与例子 |
| 算法编程 | 思路和代码是否正确，复杂度、约束与边界是否成立 |
| 场景设计 | 方案是否可行，能否解释取舍、约束与验证方法 |
| 故障排查 | 假设、证据、验证顺序与修复验证是否连贯 |
| 项目追问 | 个人实际承担部分、决策依据、实现与验证过程 |
| 行为面试 | 情境、个人行动、结果与反思是否具体、一致 |

权重按本题设置，不固定套用“覆盖度”权重。以实习岗位与题目声明的要求评价。口头说明只能支持本次可观察表现；没看代码、运行结果或实际过程时，不宣称已经验证了完整开发能力。

## 先理解回答，再评价

每次展示一道主问题，先保存原始回答，再决定直接评分还是澄清、核验。不得改写原回答；补充问答追加记录。一般一至两轮必要追问即可，避免为了问出参考答案无限加问。

- **语义不明先澄清**：例如使用者只说“控制级”，先问“你说的控制级具体指什么？能举一个实际例子吗？”。理解前保存为 `pending_clarification`，不能先给2分再用追问找理由。
- **区分澄清与提示**：请使用者解释术语、前提或自己的例子通常是中性澄清；提供关键算法、解题方向或答案片段属于实质提示。普通深入追问单独记录。不能因用了自己的术语、表达简短或接受了中性澄清而自动扣分。
- **事实有争议先核验**：数量、版本、产品限制等先明确主张和统计范围，再查匹配的官方文档、源码或其他原始资料。不能拿另一个版本或范围的证据否定回答。记录为 `pending_verification`，没有匹配证据就保持待核验；前提错误或无法公平评价时说明原因并设为无效题。
- **接受等价回答**：根据完整解释判断机制与方案是否成立。未使用参考答案术语、采用不同可行实现、没展开题目未要求的知识，都不是自动扣分理由。

澄清和核验结束后，按本题全部交流统一评价。原始回答、后续解释、提示使用情况和证据都保留。不要给每一轮单独评分后机械平均。脚本负责结构与状态约束，宿主仍须判断问题是否中性、来源是否支持结论，不能把通过结构校验当作事实核验完成。

## 反馈与分数

每题反馈分为三部分：

1. **已确认表现**：引用使用者的具体回答，说明已展示的理解或做法。
2. **有证据的问题**：指出具体错误、不可行部分或在必要追问后仍未解释的本题要求，并说明影响。扣分须有证据，不能只说“没有覆盖要点”。
3. **尚待验证能力**：说明本题没有实际考察或证据不足的能力，避免把未知写成不会。

正确的简短回答可以有充分证据；冗长回答也可能存在关键错误。使用者明确回答“不知道”或在明确目标和合理追问后暴露错误，可以据此评分；面试官没有问到、题意仍不清楚或证据不足的维度设为未评价，不补零。

全部维度完成评价时给0至10分，作为本题面试表现的辅助描述。只完成部分评价时保留已评价维度的分数与满分，总分为空，不放大成10分、不计平均分。跳过需要使用者明确提出；无效题、跳过和未答题都不计零分。不能用无效题状态回避已经证实的技术错误。

练习模式在本题完成必要澄清和追问后给反馈；模拟模式中途只提问、澄清和核验，不透露评分、参考答案或带评分倾向的评价，结束后统一复盘。参考回答和建议应贴合本题，不引申成录用概率或整体开发能力排名。

## 暂停、复盘与兼容

暂停时保留草稿，用 `sessions/show` 恢复，不为了查看结果自动结束面试。使用者明确要求结束才调用 `summary --finish`；尚待处理的回答保留原文并说明未评分。

新面试统一使用评分v2。旧评分表重新核验并 `prepare` 后才能用于新面试；旧会话按v1读取和继续，原有分数不重算。复盘显示评分版本，不将v1和v2混合计算平均分或据此宣称能力提升。薄弱题筛选只参考v2完整评分低于7分或使用实质提示的记录，澄清不会被计为提示。
